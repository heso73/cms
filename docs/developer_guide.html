CMS Developer Guide

Technical reference for integrating the Caribbean Metadata Standard into platforms, archives, and content management systems.

CMS v2.0 schema.org compliant JSON-LD 1.1 CC BY 4.0

Overview

The Caribbean Metadata Standard (CMS) is a structured taxonomy for classifying Caribbean audiovisual content. It is built as an extension of schema.org — not a replacement. A CMS document is a valid JSON-LD document that any schema.org-aware system can already partially read.

The CMS adds a custom namespace (cms:) to carry six metadata families that schema.org does not model: Linguistic, Cultural, Narrative, Rhythmic, Geographic, and Socio-historical.

Design principle: A platform that does nothing special with cms:* fields still gets a valid schema.org document. A platform that understands cms:* fields gets full Caribbean discoverability. The standard degrades gracefully.

The six metadata families

FamilyCMS prefixWhat it describes
Linguisticcms:linguistic_marker, cms:code_switchingLanguages, dialects, code-switching patterns
Culturalcms:cultural_markers[]Traditions, spiritualities, heritage markers
Narrativecms:narrative_genreGenres, story structures, Caribbean tropes
Rhythmiccms:rhythmic_tempoDialogue tempo, pacing, musicality
Geographiccms:territory, cms:environmentTerritory, environment, insular specificity
Socio-historicalcms:sociohistorical_markers[]Postcolonial markers, memory, migration

Quick start

The minimum valid CMS document requires three schema.org fields and the CMS namespace declaration.

JSON-LD · minimum valid
{
  "@context": {
    "@vocab": "https://schema.org/",
    "cms":   "https://caribbeanmetadata.org/ns/"
  },
  "@type": "CreativeWork",
  "name":  "Your content title"
}

A full production document with all six families:

JSON-LD · full example
{
  "@context": {
    "@vocab": "https://schema.org/",
    "cms":   "https://caribbeanmetadata.org/ns/"
  },
  "@type":          "Movie",
  "name":          "Anba Dlo",
  "description":   "A documentary on Vodou spirituality in rural Haiti.",
  "creator": { "@type": "Person", "name": "Claudine Moreau" },
  "datePublished": "2024-06-01",
  "inLanguage":    "ht",
  "keywords":      ["haiti", "documentary", "vodou"],

  // CMS extension — six families
  "cms:territory":             "Haiti",
  "cms:environment":           "Rural",
  "cms:linguistic_marker":     "Haitian Creole",
  "cms:code_switching":        "None",
  "cms:narrative_genre":       "Documentary",
  "cms:cultural_markers":      ["Vodou", "Afro-Caribbean spirituality"],
  "cms:rhythmic_tempo":        "slow contemplative island",
  "cms:sociohistorical_markers":["Postcolonial identity", "Memory of slavery"],
  "cms:certification":         "Gold",
  "cms:certification_date":    "2026-05-01",
  "cms:standard_version":      "CMS-2.0"
}

To embed in an HTML page, wrap in a <script> tag:

HTML embedding
<script type="application/ld+json">
{ ... your CMS JSON-LD ... }
</script>

Namespace declaration

The CMS namespace URI is the single identifier that makes all cms:* properties resolvable by JSON-LD processors. It must be declared in every document.

Correct @context
"@context": {
  "@vocab": "https://schema.org/",     // default vocab
  "cms":   "https://caribbeanmetadata.org/ns/"  // CMS prefix
}

Never use a plain string context — "@context": "https://schema.org" does not declare the CMS namespace. All cms:* properties will be silently dropped by JSON-LD processors.

Note on @vocab: Use "https://schema.org/" (with trailing slash) — not "https://schema.org". The trailing slash is required for correct property resolution.

@context declaration patterns

Pattern 1 — standalone JSON file

cms-context.json
{
  "@context": {
    "@vocab": "https://schema.org/",
    "cms":   "https://caribbeanmetadata.org/ns/"
  }
}

Pattern 2 — reference a shared context file

Referencing external context
{
  "@context": [
    "https://schema.org/",
    "https://caribbeanmetadata.org/ns/context.json"
  ],
  "@type": "CreativeWork",
  ...
}

Pattern 3 — Python generation

Python
def cms_context():
    return {
        "@vocab": "https://schema.org/",
        "cms":   "https://caribbeanmetadata.org/ns/"
    }

doc = {
    "@context": cms_context(),
    "@type":    "Movie",
    "name":     "Anba Dlo",
    "inLanguage": "ht",
    "cms:territory": "Haiti",
}

Pattern 4 — JavaScript / Node.js

JavaScript
const CMS_CONTEXT = {
  "@vocab": "https://schema.org/",
  "cms":   "https://caribbeanmetadata.org/ns/"
};

const doc = {
  "@context":       CMS_CONTEXT,
  "@type":          "Movie",
  "name":          title,
  "inLanguage":    langCode,     // must be BCP 47
  "cms:territory": territory,
};

Language codes

inLanguage requires BCP 47 (RFC 5646). Never use ISO 639-3 codes in this field — they are not recognized by Google, Bing, or any major schema.org processor.

Common mistake: Using "hat" (ISO 639-3) instead of "ht" (BCP 47) for Haitian Creole. Google will silently ignore the inLanguage field if it doesn't match BCP 47.

LanguageBCP 47 ✓ (use in inLanguage)ISO 639-3 ✗ (internal use only)

Guadeloupe Creolegcfgcf
Martinique Creolemart1259–
Jamaican Patoisjamjam

Englisheneng
Spanishesspa
Dutch / Papiamentonl / papnld / pap

To store the ISO 639-3 code alongside the BCP 47 value, use a dedicated CMS property:

Dual language coding
"inLanguage":          "ht",        // BCP 47 — required by schema.org
"cms:language_iso639_3": "hat"       // ISO 639-3 — for internal/archival use

Integration levels

Platforms and archives can adopt the CMS at three levels of commitment. Each level is independent and non-destructive to existing infrastructure.

1

Basic — accept CMS tags as keywords Hours

No schema changes. Pass cms:cultural_markers and cms:narrative_genre values into your existing keyword or subject fields (dc:subject, keywords). Minimum viable adoption.

Level 1 · SQL example
-- Store CMS tags as additional keywords
INSERT INTO content_keywords (content_id, keyword, source)
VALUES
  ('abc123', 'Vodou',           'cms:cultural_markers'),
  ('abc123', 'Documentary',      'cms:narrative_genre'),
  ('abc123', 'Haiti',            'cms:territory');
2

Structured — map CMS families to dedicated columns Days

Add columns or properties for each CMS family. Enables filtered queries by territory, language, genre.

Level 2 · SQL schema
ALTER TABLE content
  ADD COLUMN cms_territory          VARCHAR(100),
  ADD COLUMN cms_language_bcp47     VARCHAR(20),
  ADD COLUMN cms_narrative_genre    VARCHAR(100),
  ADD COLUMN cms_rhythmic_tempo     VARCHAR(60),
  ADD COLUMN cms_certification      VARCHAR(20),
  ADD COLUMN cms_standard_version   VARCHAR(10);
3

Native — full six-family integration Weeks

First-class CMS fields in your data model, search index, and recommendation engine. Full Caribbean discoverability. Output CMS-compliant JSON-LD from your content API.

Level 3 · API JSON response
// Your content API endpoint returns CMS JSON-LD directly
GET /api/content/abc123?format=jsonld

{
  "@context": { "@vocab": "https://schema.org/", "cms": "https://caribbeanmetadata.org/ns/" },
  "@type": "Movie",
  "name": "Anba Dlo",
  "cms:territory": "Haiti",
  "cms:certification": "Gold"
  // ... full document
}

CMS → Dublin Core mapping

Use the conversion script cms_to_dublin_core.py for automated conversion. The table below shows the full mapping logic.

Conversion script: python cms_to_dublin_core.py input.json --format both — produces _dublin_core.xml (OAI-DC) and _dublin_core.csv.

name→dc:titleDirect
description→dc:descriptionDirect
creator.name→dc:creatorPerson or Organization
datePublished→dc:dateISO 8601
inLanguage→dc:languageBCP 47 + label
url→dc:identifierURI
@type→dc:formatschema: prefix added
keywords[]→dc:subjectOne entry per keyword
cms:cultural_markers[]→dc:subjectPrefixed CMS:cultural:
cms:sociohistorical_markers[]→dc:subjectPrefixed CMS:sociohistorical:
cms:narrative_genre→dc:type + dc:subjectBoth fields populated
cms:territory + cms:environment→dc:coveragespatial: qualifier
cms:certification→dc:relationCMS-Certification: prefix
cms:standard_version→dc:sourceWith namespace URI

CMS → EBUCore mapping

EBUCore is the standard used by broadcasters, public archives, and audiovisual institutions. CMS maps cleanly to EBUCore 1.6.

Certification levels

CMS certification is assigned through the official process at caribbeanmetadata.org. The level reflects the depth of cultural anchoring in the metadata.

Bronze
Core fields complete. Territory and language declared.
Silver
+ Narrative genre and at least 2 cultural markers.
Gold
+ All six families populated. Rhythmic and socio-historical included.
Platinum
+ Expert-validated. Community-reviewed. Full corpus tagging.

Common errors

Error 1 — Plain string @context

Wrong ✗
"@context": "https://schema.org"   // CMS namespace not declared
Correct ✓
"@context": { "@vocab": "https://schema.org/", "cms": "https://caribbeanmetadata.org/ns/" }

Error 2 — ISO 639-3 in inLanguage

Wrong ✗
"inLanguage": "hat"   // ISO 639-3 — not recognized by Google
Correct ✓
"inLanguage": "ht"    // BCP 47 — correct for Haitian Creole

Error 3 — cms: prefix without namespace declaration

If "cms": "https://caribbeanmetadata.org/ns/" is missing from @context, all cms:* properties are treated as arbitrary strings and dropped by JSON-LD processors. The document remains valid schema.org JSON-LD but all CMS information is lost.

Error 4 — additionalProperty wrapper (deprecated)

Old pattern (v1.x) ✗
"additionalProperty": {
  "@type": "PropertyValue",
  "name": "cms:rhythmicTempo",   // wrong: name is not a namespace
  "value": "syncopated"
}
Current pattern (v2.0) ✓
"cms:rhythmic_tempo": "syncopated"   // first-class property
